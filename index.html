Open, community-built AI inference for everyone

A community proposal for open-source, decentralized LLM inference, settled on Arbitrum One. Comuns is Portuguese for “commons”.

Pictured: a mesh of nodes. A wallet sends an encrypted prompt through a relay run by a different operator to the node it chose, and the sealed answer comes back the same way.

Read the pitch deck How to contribute

Why

The closed door

Hosted models concentrate capability in a few providers. A cheap API still lets the provider read every prompt and refuse service.

Comuns does not claim a lower price than hosted APIs. The case is control: code, specifications and economics that anyone can inspect, run and fork.

The repository is the proposal. Every claim lives in a document anyone can challenge.

How

How one prompt flows

By default one node runs a request: pick a model, then a node from its pool. Collective answers and decomposed plans are opt-in.

Principles

What the proposal commits to

  • Anonymous by default

    The node you pick can read your prompt, but neither it nor the chain should learn who sent it. Standard mode hides who asked, not what was asked.

    Attested (TEE) mode is opt-in: there the node should not be able to read the prompt either, barring a physical attack on the hardware.

    The anonymous-by-default decision record

  • Encrypted transport

    Two-way encryption is RFC 9180 HPKE, and client-to-node traffic uses RFC 9458 Oblivious HTTP.

    The relay sees your network address and not your prompt. The node sees your prompt and not your network address.

    The HPKE transport decision record

  • ETH on Arbitrum One

    Arbitrum One settles sessions in ETH. The chain sees a session, never a payer.

    Protocol fee: zero. The inference payment is not L2 gas.

    The Arbitrum One settlement decision record

  • No token

    v1 does not issue a protocol token. No token gate and no coin vote: a class S operator has an equal voice.

    The no-token decision record

  • Rust nodes, pluggable backends

    Inference runs off-chain in a Rust node with pluggable backends.

    Rust alone is not claimed to make inference faster; the kernels do the work.

    The node design document

  • Hardware classes S to X

    Participation from CPU-only class S to multi-GPU class X, subject to measured capability and model fit. Stronger hardware charges more for the same model and weaker hardware charges less.

    CPU-only participation is a target to be validated. Classes come from a public self-benchmark, which is not an unfakeable proof.

    Hardware classes and benchmarks

  • Open source

    Apache-2.0 for code and documents; DCO sign-off, no CLA.

    If the community disagrees with a direction, it can fork the specifications, the contracts and the node.

    Contributing guide

  • Governance by CIPs

    Decisions are CIPs: Draft, Review, Last Call, Final. Working groups review; a CIP decides.

    Anyone can write a CIP. Decisions follow the CIP process and rough consensus in working groups, not coin votes.

    Governance document

Status

What exists today, and what does not

Exists

  • A draft proposal: documents, decision records and CIPs, written in the open.
  • Documentation checker scripts in the repository.
  • A pitch deck, written in Markdown and rendered to a self-contained HTML page.

Does not exist

  • No protocol implementation runs yet.
  • No contract is deployed, no node exists, no relay exists.
  • No maintainer is seated, no audit has been performed and no mainnet date exists.
  • Price bands are unset. Class claims are self-benchmarks, fakeable.

We make no claim of a mainnet date, an audit, a grant, a partnership, existing users or a price lower than hosted APIs. No maintainer is seated yet, and contributors may not come; the plan states its risks openly.

Get involved

Build it with us

Comuns is built by whoever shows up and writes in public. You do not need a hardware class, a stake, or a holding to review, comment or propose. The only channels are issues and CIP comments on the repository.

For contributors

  1. Review CIP-0003 (pull request #7). A Draft proposal for seating the first maintainer. Any person other than the author can review it: a public comment that approves or names a blocking objection.
  2. Comment on the CIPs. None are Final.
  3. Join a working group: Protocol, Node, Cryptography, Contracts, Applications or Documentation. Say so in a public issue or on a relevant CIP.
  4. Read the contributing guide. Contributions use the Developer Certificate of Origin; there is no CLA.
  5. Later, run a node on any hardware class. CPU-only class S is still a target to be validated. See the project plan for its proposed phases.

For supporters

  1. Read the pitch deck and the project plan.
  2. Open an issue to talk. Issues are for document comments and documentation flaws.

This draft names no discussion channel beyond issues and CIP comments on the repository.
